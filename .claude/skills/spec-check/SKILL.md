# spec-check — есть ли под это спека

Советник, не ворота. Ничего не блокирует, доску сам не правит, ответ пользователя не подменяет. Задача скилла — задать вопрос, который иначе не задаётся: **под то, что мы сейчас планируем, раздел спеки уже есть или его нет?**

Конфликт задачи со спекой ловится глазами, а глаза его не ловят: спеку не открывают, когда не помнят, что она про это. Матч по лексике эту память заменяет частично — он ошибается в обе стороны, поэтому его ответ идёт пользователю как вопрос, а не как вывод.

## Когда запускать

- **В plan mode, до `ExitPlanMode`** — когда план уже сложился, но ещё не подтверждён. Это последняя точка, где спеку дёшево прочитать до работы, а не после.
- **При заведении change'а** — до того, как у записи появится `delta`.
- По прямой просьбе: «есть ли спека под это», «проверь спеку по задаче #N», `/spec-check`.

Не запускать: на мелкой правке без плана, в чужом проекте без реестра спек (см. «Когда молчать»).

## Что запускать

`<cli>` — то же, что и везде в проекте: в этом репозитории `node scripts/cli.mjs`, в других — путь, который выдаёт SessionStart-хук.

```
<cli> spec match "<заголовок change'а или subject задачи>"   # текст руками
<cli> spec match --task <N>                        # subject + description с доски
<cli> spec match "<текст>" --json --limit 5        # машинный ответ
```

**Подавать короткий текст.** Счёт — доля значимых слов запроса, покрытая разделом, поэтому страница прозы размазывается по десятку разделов и уводит верный ответ под порог. Заголовок change'а, subject задачи, заголовок шага плана — да. Весь `vision` целиком — нет.

Если планируется несколько шагов про разные области — прогнать по одному запросу на область, а не один общий.

## Три развилки

### 1. Кандидаты есть, задача не слинкована

```
tasks#done-gate  0.57  [инварианты]  Инварианты закрытия
    заголовок: закрытия
    текст: prerequisite, отказ
```

- Прочитать раздел целиком: `<cli> spec show tasks#done-gate`. Не пересказ из вывода матча — сам текст; матч знает только слова.
- Сказать пользователю, что нашлось и **задевает ли план этот раздел на самом деле** — это решение, а не совпадение слов. Раздел может совпасть по лексике и не иметь отношения к делу.
- Если задевает — предложить привязку и назвать команду:
  `<cli> change set spec c#N tasks#done-gate` — раздел задевает работу целиком;
  `<cli> todos set spec <задача> tasks#done-gate` — раздел задевает именно этот шаг.
  Привязывается **запись change'а**, когда план заводит новую работу: задачи внутри читают адреса с неё, и отдельная привязка каждой из них только разойдётся с ней. Задача берёт свой адрес, когда её шаг задевает раздел, которого не задевают соседние.
- Привязка ставится **после того, как план записан**: запись change'а заводит `apply` на выходе из plan mode, до этого адреса `c#N` ещё нет. Раньше — только назвать адрес раздела и держать его в плане словами.
- Адрес брать из вывода матча копией, а не по памяти: `todos set spec` опечатку поймает, `change set spec` — нет, он берёт строку как есть.

### 2. Кандидатов нет

```
раздела под это нет: ни один не набрал порога
  ближайший — tasks#context (0.21, порог 0.3); совпало: контекст
  Это повод завести раздел (домен-кандидат tasks) …
```

Это главный полезный ответ команды, а не пустой.

- Сказать прямо: спеки под это нет.
- Спросить пользователя: **заводим раздел или нет?** Назвать домен-кандидат из вывода и то, чем раздел был бы — `требования`, `устройство` или `инварианты`.
- Рождение спеки ленивое (README §8): раздел появляется по факту работы над областью, из того, что сессия и так узнала. Заводить раздел авансом, до работы, не надо — надо решить, что он появится по её итогу, и сказать это вслух.
- Если пользователь говорит «не надо» — записать почему. Одной строкой в `delta` change'а или комментарием к задаче: `<cli> todos comment add <N> --text "спеки под это нет намеренно: …"`. Иначе следующий заход задаст тот же вопрос заново.
- Посмотреть на «ближайший» из вывода: он подписан как промах, но при счёте близко к порогу это может быть верный раздел, которому не хватило слов. Открыть и посмотреть стоит.
- Пустой ответ не пропадает: каждый прогон матча пишется в счётчик, и `<cli> spec coverage` показывает, какие запросы приходили без ответа повторно и сколько их было подряд. Запрос, прозвучавший третий раз, — это уже не вопрос «заводить ли раздел», а заявка на него; сослаться на счётчик здесь дешевле, чем уговаривать по одному случаю.

### 3. Задача уже слинкована

Вывод начинается со строки `уже слинковано: <адрес>`, а сам раздел помечен `← УЖЕ СЛИНКОВАН — сверка, не находка`.

- Это не находка, повторять её пользователю как открытие не надо.
- Смотреть надо на **остальных кандидатов**: задача может задевать раздел, о котором никто не подумал, когда ставил привязку. Если такой есть и он правда задевается — предложить добавить второй адрес (поле `spec` принимает список через запятую).
- Если слинкованный раздел в кандидатах не появился вовсе — это тоже сигнал: либо привязка не про эту работу, либо текст плана ушёл в сторону от того, что было слинковано. Сказать об этом, не молчать.

## Чего скилл не делает

- **Не пишет на доску сам.** `todos set spec`, `todos comment add`, правка спеки — только после явного «да» от пользователя.
- **Не блокирует план.** Отсутствие спеки — не повод отложить ExitPlanMode.
- **Не правит `docs/specs/**` по ходу.** Раздел заводится под задачей, которая его заполняет, а не в plan mode.
- **Не пересказывает раздел вместо чтения.** Вывод матча — список слов; решение принимается по тексту раздела.

## Когда молчать

- `spec match` ответил «в реестре нет ни одного домена» — в этом проекте спек нет, вопрос не про него. Ничего не говорить.
- «в тексте меньше двух значимых слов» — по такому запросу нельзя судить; либо дать текст побольше, либо не поднимать тему.
- «все значимые слова запроса встречаются во всех разделах сразу» — **это не «спеки под это нет»**. Счёт стоит на редкости слова, а в реестре из одного-двух разделов редких слов нет: различать нечем, и команда честно воздерживается — за этой строкой не печатается «Это повод завести раздел». Читать её как отсутствие раздела и предлагать завести новый — значит выдать за находку то, чего матч не увидел. Пока реестр так мал, разделы заводятся по работе, а не по подсказке.
- Скилл уже отработал в этой сессии по этой же теме — второй прогон ничего не добавит.

## Порог и его цена

Порог `--min` (по умолчанию 0.3) подобран на дюжине точек одного репозитория: девять задач с уже проставленной привязкой и три заведомо посторонних текста. Классы разошлись на одну сотую — это не разделение, а совпадение. Отсюда правила чтения вывода:

- счёт — не вероятность и не уверенность, а доля совпавших слов; сравнивать его между разными запросами бессмысленно;
- промах ниже порога всё равно печатается строкой «ближайший» — читать её;
- сомнение решается открытием раздела (`spec show`), а не порогом. `--min 0` показывает всё подряд, когда надо посмотреть глазами.
