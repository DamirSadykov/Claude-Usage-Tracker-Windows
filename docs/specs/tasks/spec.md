> Отличие от [task-pipeline.md](../../task-pipeline.md): гайд учит «как

## model — Модель и хранение

part: устройство

- Задача — узел направленного ациклического графа (DAG). Доски разделены по
  проектам, плюс одна глобальная (project-less) доска; задача принадлежит
  ровно одной.
- У задачи есть UUID (`id`) и монотонно растущий человеко-читаемый номер `#N`
  (не переиспользуется после удаления задачи). В прозе задача упоминается как
  `t#N`; голый `#N` читается как GitHub PR/issue и задачей не считается — эту
  разницу держит резолюция inline-ссылок (`todos.mjs::inlineRefNumbers`).
- Хранилище — один файл `todos.json` в data-каталоге приложения
  (`{version: 1, todos: [...]}`). Единственные писатели — CLI трекера
  (`scripts/cli/todos.mjs` и его сателлиты) и само приложение
  (`src-tauri/src/todos.rs`); правка файла руками не поддерживается —
  конкурентная запись портит общий файл. Запись атомарна (tmp-файл + rename).
  UI перечитывает доску вживую по изменению файла на диске.
- Локатор задачи принимает три формы — id, голый номер, `#N` — везде, где
  команда берёт `<task>`; резолюция общая (`resolveTask`).
- **Новое поле обязано появиться в обеих схемах сразу** — и в CLI, и в
  структуре `Todo` приложения. Писатель, который поля не знает, стирает его на
  первом же сохранении: файл переписывается целиком. Мало объявить поле — в
  `upsert_todo` нужен и перенос существующего значения, когда фронтенд прислал
  пустое, иначе правка задачи из UI обнуляет объявленное через CLI. Так уже
  сделано для `produces`, `verify`, `outcome` и `spec`. Тесты CLI такую потерю
  не ловят: стирает её другой писатель.
- Пустые поля в файл не пишутся (сериализация пропускает unset-поля), поэтому
  файл остаётся читаемым при ручном diff.

## fields — Поля задачи и их роли

part: требования

Четыре текстовых поля несут четыре разные роли; один и тот же текст не живёт
в двух полях одновременно — сеттеры отказывают дубль явно (`refuseIfDuplicate`):

| Поле | Роль |
|---|---|
| `description` | WHAT & WHY; у change-root — дельта захода (см. `changes`) |
| `plan` | только HOW: то, что записал ритуал plan mode (см. `plan-mode`); переписывается при перепланировании |
| `handoff` | батон-результат для зависимых задач (см. `handoff`) |
| `comments` | журнал: решения, смена скоупа, находки; только добавление |

Прочие скалярные поля пишутся через единственный сеттер
`todos set <field> <task> <value>` (`scripts/cli/todos.mjs::SET_FIELDS`):
`status` и производный от него `status_history` (лог переходов — источник для
`cost`), `priority` (`high|medium|low|none`), `kind` (см. `kind`),
`scheduled_for` (дата — попадает в «⏰ due» контекста сессии, см. `context`),
`change` (см. `changes`), `project`/`from`, `created_by`, `spec` (адрес(а)
раздела спеки, см. `spec-registry`).

Рёбра графа (`depends_on`, `links`) пишутся отдельными командами `dep`/`ref`,
не через `set` (см. `edges`). Поля языка процесса — `produces`, `verify`,
`retry_limit`, `budget_usd`, `parallel_limit`, `on_issue`,
`outcome`/`outcome_at`/`outcome_reason` — разобраны отдельно, см.
`process-language`.

Команда без аргумента (`todos set`) печатает полный список полей, их
допустимые значения и правило каждого — список сгенерирован из таблицы
`SET_FIELDS`, поэтому не может разойтись с кодом.

## statuses — Статусы: две оси

part: требования

- Колонка (kanban): `backlog | queue | in_progress | review | done` — куда
  задачу положил человек (или CLI). На графе (`GraphView.vue`) это заливка
  узла.
- Pipeline-состояние: `blocked | ready` — выводится из графа, не хранится
  (`todos.mjs::isReadyNode`). `blocked` = есть незакрытый прямой prerequisite;
  `ready` = все закрыты (задача без рёбер — ready). На графе — точка в углу
  узла.
- Оси независимы: задача может быть `in_progress` и `blocked` одновременно —
  граф это честно показывает, а не скрывает.
- Легаси-статус `pending` (записанный до появления колонок) на чтении
  мигрирует в `backlog` — и в CLI (`col()`), и в приложении, и в
  SessionStart-хуке.

## edges — Рёбра графа

part: требования

- **dep** (`depends_on`): блокирующее ребро «A ждёт B» (`dep add <A> <B>`).
  Ацикличность (`depReaches`) и принадлежность одной доске проверяются при
  записи; нарушение — отказ. Отсутствующий (удалённый) prerequisite не
  блокирует.
- **ref** (`links` + inline `t#N` в description/plan): неблокирующая ссылка
  «имей в виду»; может пересекать доски; в вывод blocked/ready не входит.
  Inline `t#N` рисует только ref-ребро — блокирующее ребро создаётся
  исключительно командой `dep add`. `ref rm` снимает только явную ссылку —
  inline-упоминание продолжает рисовать ребро, пока не изменён текст.
- Критерий выбора: «B должна закончиться до старта A» → dep; «A просто хочет
  видеть B» → ref.
- `todos apply` и plan-режим переводят `needs:` шага исключительно в
  dep-рёбра, никогда в ref (см. `process-language`, `plan-mode`).

## done-gate — Инварианты закрытия

part: инварианты

- **done-gate**: перевод в `done` отклоняется, пока не закрыт хотя бы один
  прямой prerequisite (`setStatus` в `todos.mjs`); отказ перечисляет
  блокирующие задачи по номеру и статусу. Транзитивная честность держится
  индукцией: честно закрытый прямой prerequisite ручается за свой хвост.
  `--force` — явное исключение (устаревший prerequisite, работа сделана вне
  конвейера); частый `--force` означает, что рёбра врут.
- `review` ≠ `done`: prerequisite в review всё ещё держит зависимых — так же
  и в headless-раннере (`run.mjs`), где нода в review — гейт, не готовая
  работа.
- `ready` = каждый prerequisite `done`; задача без рёбер — ready.
- Тот же принцип «прямой prerequisite ручается за хвост» держит и раннер:
  `frontierOf` берёт только прямые рёбра, `isReadyNode` — общая функция для
  доски, `ready`, `pipeline` и раннера — расхождения между ними быть не может.

## kind — Kind: авторитет закрытия

part: инварианты

- `manual` (по умолчанию, пустое поле) — человеческий гейт: сессия делает
  работу, но переход `review → done` оставляет пользователю. Красный/жёлтый
  хвост ниже по графу — гейт **работает**, а не сломан.
- `auto` — узел, который сессия или раннер может выполнить без присмотра,
  проверить и закрыть сам. Ставится только там, где успех верифицируем:
  `auto` без объявленного `verify` предупреждается при записи (`setKind`) и
  на деле выполняется раннером как гейт (`isGate` в `run.mjs`) — авторитет
  закрытия идёт от проверки, а не от одного флага.
- На графе auto-узел помечен `⚡`.
- Ошибочное авто-закрытие компаундится вниз по цепочке до ближайшего
  manual-гейта — так и headless-раннер, и живая сессия читают одну и ту же
  таблицу `SET_FIELDS`, поэтому правило не может разойтись между путями записи.

## handoff — Handoff-батон

part: требования

- `handoff` задачи — что она **произвела**: файлы/пути, интерфейсы, решения,
  грабли, следующий шаг. Пишется для задач, которые от неё зависят; батон, не
  журнал. Пустой допустим. `handoff_at` — отдельная метка (не `updated_at`),
  по которой Stop-хук отличает свежий батон этой сессии от унаследованного.
- Перевод задачи в `in_progress` автоматически печатает батоны её прямых
  prerequisites (`formatInheritedHandoff`). Читаются только прямые: длинная
  цепочка контекста собирается тем, что батон — авторская проза и сам
  ссылается на `t#N` выше по графу.
- Stop-хук (`scripts/cli/stop-hook.mjs`) блокирует завершение сессии, которая
  двигала задачу (атрибуция — по транскрипту, не по времени), но не оставила
  свежий содержательный батон; проверяет и свежесть (`handoff_at` этой
  сессии), и содержательность (не пересказ subject/description, есть
  следующий шаг).
- В автономном прогоне (`todos run`) шаг пишет батон секцией `## HANDOFF` в
  своём ответе (`run-step.mjs::extractHandoff`), а на доску его кладёт сам
  прогон (`run.mjs::recordBaton`) — у шага нет shell. Шаг, не написавший
  секцию, отмечается в отчёте прогона («NO baton»), а не проходит молча;
  отказ записи батона отмечается отдельно («baton REFUSED»).

## changes — Change: дельта к спеке

part: устройство

- Change — обычная root-задача, которая `depends_on` всех своих детей;
  отдельной сущности нет, агрегация = dep-рёбра. Из done-gate следует: root
  закрывается последним.
- Root помечается флагом `change` (`todos set change <task> on|off`,
  `add --change`) — флаг нужен потребителям, чтобы находить агрегатор
  детерминированно, а не угадывать, какая из задач выше по графу «та самая».
  Постановка флага на root без детей предупреждает, а не отказывает.
- Change несёт **дельту**: что меняется в этом заходе и почему сейчас. Тем
  он и отличается от прежней «темы», которая была носителем смысла:
  долгоживущее «что должно быть и почему» живёт в разделе спеки, на который
  смотрит поле `spec` (см. `spec-registry`), и переживает change, а сам
  change умирает вместе со своим графом.
- Флаг читается через единственную функцию `isChangeRoot`, которая понимает
  и legacy-поле `theme: true` — доски, заполненные до переименования темы в change,
  продолжают работать без разовой миграции файла; запись всегда идёт в
  `change`, поэтому запись задачи выправляет её сама. Снятие флага удаляет
  оба поля, чтобы старое не воскресило снятое.
- **Description root'а читается ВВЕРХ**: при переводе ребёнка в `in_progress`
  печатается description ближайшего change-root'а вверх по каждой ветке
  (`changeRootsFor`; внешний change поверх внутреннего не виден);
  SessionStart-хук повторяет его для показанных `in_progress`-задач;
  `todos vision <task>` перечитывает по запросу.
- Канал несёт не только description: рядом печатается раздел спеки по полю
  `spec` (см. `context`) — дельта захода и долгоживущее состояние приходят
  вместе, но остаются разными текстами в разных местах.
- Handoff root'а — обычный батон вниз тем, кто зависит от самого root'а.
- Хотя рёбра дети→root существуют в данных, на графе Deps change с 2026-07-20
  рисуется секцией-аккордеоном (построено —
  `GraphView.vue::changeSections`), а не терминальным узлом (см. `ui`): рёбра
  член→root не рисуются, `⊖` схлопывает секцию в одну карточку.

## process-language — Язык объявлений на узле

part: требования

Узел графа может нести восемь дополнительных полей — объявления, которые
описывают КАК шаг должен быть выполнен и проверен, ДО начала работы. Это
отдельный слой от `handoff` (отчёт ПОСЛЕ работы): объявление — обещание,
батон — результат. Живут в `todos.json` рядом с остальными полями; пишутся
через `todos set <field> <task> <value>`
(`scripts/cli/todos.mjs::SET_FIELDS`, все — с флагом `declaration: true`).

- **`produces`** (список путей/интерфейсов/записей) — что шаг обещает
  произвести. Пишется командой `produces add/rm/list`; читает и сверяет
  `todos outcome` (реконсиляция «обещано → произведено → потреблено», ниже).
- **`verify`** — команда, чей exit-код решает исход: 0 = `ok`, иначе `issue`.
  Пустая строка снимает объявление; снятие `verify` у `kind: auto` понижает
  узел до гейта (см. `kind`) — `setVerify` говорит об этом явно.
- **`retry_limit`** — сколько попыток разрешено узлу, прежде чем раннер
  паркует его в `review`. Отсутствие объявления ЗАПРЕЩАЕТ переход `?issue`, а
  не разрешает бесконечный: попытка M+1 никогда не начинается
  (`run.mjs::runOne`).
- **`budget_usd`** — потолок расхода: на обычном узле свой, на change-root —
  потолок всей группы. Достигнут — мягкая остановка на границе шага, откат
  уже потраченного не делается.
- **`parallel_limit`** — сколько шагов change'а раннер может вести
  одновременно; читается только с change-root (`setParallel` предупреждает на
  обычной задаче, но не отказывает). Параллелизм сам по себе не объявляется — это отсутствие ребра
  между шагами; объявляется только потолок.
- **`on_issue`** — куда идёт управление при исходе `issue` (переход уровня
  прогона, НЕ ребро `depends_on` — запись в `depends_on` сломала бы
  ацикличность). Требует уже объявленного `retry_limit`; цель — задача той же
  доски, не сам узел.
- **`outcome`/`outcome_at`/`outcome_reason`** — не объявление, а РЕЗУЛЬТАТ
  реконсиляции: пишутся командой `todos outcome <task> --write`
  (`scripts/cli/outcome.mjs`), которая сверяет объявленное `produces` с
  реально изменёнными файлами по транскриптам сессий (в пределах блока
  `(задача, сессия, интервал)`, см. `cost`) и с фактом потребления
  зависимыми задачами. Предикат `ok`/`issue` считается ТОЛЬКО когда `verify`
  действительно прогнан (`--verify ok|issue` от раннера) — сам `outcome.mjs`
  команду не запускает.
- Все declaration-поля отказывают запись на уже закрытом (`done`) узле
  (`refuseIfClosed`): объявление — обещание ДО работы, а на закрытом узле
  обещать нечего.
- `todos apply <file>` (см. `plan-mode`) и `todos lint`
  (`scripts/cli/lint.mjs`) читают и проверяют этот язык через общую таблицу
  правил `graph-rules.mjs` — так текст отказа у файла-плана, у живой доски и
  у сеттера один и тот же, а не три независимые копии.
- `todos pipeline` печатает, что объявлено на каждом открытом узле доски
  (`formatDeclarations`) — единственный «дисплей» языка процесса без ухода в
  `--json`.

## plan-mode — Plan mode: ритуал формирования задач

part: устройство
refs: usage-tracker#cc-integration

- План — не текст для пользователя, а файл, который трекер записывает: YAML,
  один шаг = одна задача (`docs/plan-format.md`). Хук на входе в plan mode
  (`scripts/cli/plan-hook.mjs::enter/prompt`) не повторяет формат в каждой
  инъекции — один раз за сессию отсылает к `docs/plan-format.md` и просит
  прочитать его.
- Формат: `change` (группа), `vision` (абзац WHAT&WHY), `parallel`/`budget`
  (потолки группы), `steps` — по одному на шаг: `title` или `task: <N>` (шаг
  продолжает уже существующую задачу), `why` (обоснование и риск шага —
  уходит в `description` задачи, если оно там ещё пустое), `needs`
  (блокирующие рёбра, ТОЛЬКО реальные блокеры) и полный набор объявлений
  языка процесса — `produces`, `verify`, `retry`, `on-issue`, `kind`, `budget`
  (см. `process-language`).
- **Гард до показа пользователю**: `scripts/cli/plan-guard.mjs` —
  PreToolUse-хук на `ExitPlanMode` — проверяет план ДО того, как его увидит
  пользователь; план, который не парсится как файл языка (или парсится, но
  нарушает правило), отклоняется с указанием правила, и подтверждение так и
  не показывается. Правила те же, что у `todos apply`/`todos lint` (общий
  `graph-rules.mjs`) — формулировка отказа не расходится между тремя точками
  входа. Единственный путь наружу без записи работы — строка
  `discussion: <причина>` первой строкой: такой план проходит гард нетронутым
  и ничего не пишет на доску; голый флаг без причины отклоняется.
- **Запись одобренного плана — не ручная.** Хук на выходе
  (`plan-hook.mjs::exit`) сам читает текст плана и вердикт харнесса
  approved/rejected из `tool_response` (`tool_input` в этом событии приходит
  пустым — известный разрыв бриджа, полагаться на него нельзя), сам
  прогоняет `applyDocument` (`scripts/cli/apply.mjs`) и записывает граф —
  эквивалент `todos apply <файл>.yaml --go` — без участия сессии. Инструкция
  «сохрани файл и запусти apply руками» остаётся ТОЛЬКО запасным путём — для
  плана, который хук не смог однозначно прочитать как документ языка.
- Повторное применение того же файла ОБНОВЛЯЕТ граф, а не создаёт дубликат:
  шаг ищет свою задачу по `task: <N>`, если он есть, иначе по заголовку —
  сначала среди детей change'а, затем по всей доске проекта.
- Каждый вызов exit-хука оставляет строку в журнале `plan-events.jsonl`
  (`noteExit`) — какая ветка сработала (`recorded`/`instruction`/
  `discussion`/`not-approved`/`record-failed`/`silent`), сколько текста плана
  пришло, что было в `tool_response`. `todos adoption` читает этот журнал,
  чтобы отвечать «ритуал вообще срабатывает» без ре-прогона транскриптов.
- Plan mode не обязателен: задача, созданная без него, работает как обычно —
  просто структура (declarations, dep-рёбра) не записывается бесплатно.

- Предупреждения-кейсы от KB-совместимого CLI (`matchPlanCli` в настройках)
  экономят повтор чужой ошибки: план прогоняется через `match-plan`, найденное
  впрыскивается в контекст и просится в комментарий задачи; ноль находок —
  тишина, сбой матчера никогда не блокирует запись.
- ⚠ разрыв, проверен 2026-08-03: ветка предупреждений берёт текст плана из
  `tool_input.plan` (`plan-hook.mjs`, `sub === "exit"`), а харнес кладёт план в

## context — Каналы контекста сессии

part: устройство

- **SessionStart-хук** (`scripts/cli/hook.mjs`): инструкция по CLI (контракт
  «как редактировать» идёт ПЕРВЫМ, чтобы обрезка инъекции не съедала его) +
  срез доски проекта — сначала ⏰ due/просроченные (любая колонка, любой
  приоритет), затем queue-задачи, которые являются текущими корнями графа
  (все prerequisites закрыты), плюс все `in_progress`, отфильтрованные по
  настройке приоритетного порога (`taskContextMinRank`); due-слой порог не
  проверяет. Срез ограничен: не более 10 задач (`CAP`), только заголовки,
  обрезанные до ~100 символов (`SUBJECT_MAX`); полная доска — `todos list`.
- Та же инъекция несёт description change-root'а (см. `changes`) для показанных
  `in_progress`-задач и привязку сессии к задаче (`bindSessionToTask`) —
  единственную in_progress-задачу сессия получает автоматически, при двух и
  более — предупреждение с просьбой выбрать через `todos take`.
- **Перевод в `in_progress`**: авто-печать унаследованных батонов (`handoff`)
  и description change-root'а (`changes`) — тот же анкор, что и в `hook.mjs`, но по факту
  перехода статуса (`setStatus` в `todos.mjs`), не по старту сессии.
- **Раздел спеки приходит тем же каналом** (`formatSpecSections`):
  печатается адресованный раздел ЦЕЛИКОМ по полю `spec` задачи, а если оно
  пусто — по полю `spec` её change-root'а (`specAddressesFor`). Наследование —
  замещение, не объединение: собственный адрес задачи отменяет адрес root'а
  целиком, поэтому один и тот же раздел не печатается дважды. Строки `refs`
  внутри раздела остаются адресами: текст соседнего раздела не разворачивается
  ни при каких условиях — за этим стоит бюджет контекста
  ([README.md](../README.md) §7), а не экономия ради экономии.
- Все три ответа реестра различимы и ни один не молчит: раздел найден —
  печатается; адреса нет — печатается причина отказа; раздел объявлен, а
  текст недоступен (внешний репозиторий не настроен) — печатается, чего именно
  не хватает. Молчаливо пустая инъекция была бы неотличима от «спеки нет».
- **Stop-хук** (`scripts/cli/stop-hook.mjs`): блокирует завершение сессии,
  которая двигала задачу, но не оставила свежий содержательный handoff;
  жалобы конкретны (батон пересказывает subject/description; нет следующего
  шага). Атрибуция «сессия двигала задачу» — по транскрипту (какие
  `todos set status` реально прогнала ЭТА сессия), не по временному окну.
- Отключение инъекции (не привязки — та пишется всегда: стоимость должна
  атрибутироваться независимо от болтливости хука) — настройка
  `hookContextEnabled`.

## triage — Триаж

part: устройство

- Ночной триаж — встроенный планировщик приложения (не Windows Task

  экспортирует срез доски (`triage_schedule.rs`), агент читает его и пишет

## cost — Стоимость задач

part: устройство
refs: usage-tracker#analytics

Сессии атрибутируются задачам по трём источникам, в порядке убывающего
приоритета (`src-tauri/src/task_cost.rs::judge`/`judge_journal`):
(0) журнал привязок `task-sessions.jsonl` — сессия, у которой есть биндинг,
судится ТОЛЬКО по нему; (1) прямое доказательство из транскрипта — сессия
перевела ровно одну задачу в рабочий статус; (2) то же, без переводов
статуса — ровно одна задача была прокомментирована/получила handoff;
(3) откат на пересечение по времени — ровно одна задача того же проекта была
`in_progress` в окне сессии И сессия её упомянула (упоминание обязательно —
иначе случайная сессия того же проекта наследует чужую стоимость). Сессия,
чьи улики называют ≥2 задачи в одном уровне, — «неоднозначная», её токены
никогда не размазываются по кандидатам.

Единица разреза — **блок**: `(задача, сессия, интервал)`, полученный
сворачиванием журнала `task-sessions.jsonl` (`task_sessions.rs::blocks`).
Открывает блок событие `start`; закрывает его `start` любой другой задачи той
же сессии (сессия работает над одной задачей за раз) или `end` ТОЙ ЖЕ
задачи — `end` другой задачи блок не закрывает (иначе живой блок обрывается
тем, что не имеет к нему отношения).

Внутри блока расход раскладывается по исполнителям: главная сессия — строка
с `agent_id = None`, и по одной строке на каждый экземпляр субагента
(`analytics.rs::block_agents`, join `cc_usage` × `cc_agent`). Субагент
биллится под `session_id` родителя, поэтому исполнителей различает `agent_id`
(`agentId` транскрипта), а не тип агента — двух субагентов одного типа тип не
развёл бы. Манифест `agent-<id>.meta.json` (`cc.rs::parse_agent_meta`) даёт
тип, `toolUseId` породившего вызова и `description`, с которым агент был
запущен; строки разбивки суммируются обратно в итог блока.

⚠ направление: сам блок пока не ключуется агентом — два параллельных шага
ОДНОЙ сессии всё ещё делят один блок; разбивка по `block_agents` показывает,
что внутри него смешано, но не переносит расход на разные ЗАДАЧИ.

`get_task_blocks` (Tauri-команда) отдаёт блоки одной задачи с их
стоимостью/токенами/tool-вызовами; `get_task_graph` — то же для целого change'а,
поверх графа зависимостей, в виде mermaid/d2 для внешних потребителей.

  не по одному, потому что шаблонность видна только рядом (README §9).
- Реестр во вкладке НЕ разбирается заново: команды `spec_projects` /
  `spec_domains` / `spec_section` (`src-tauri/src/spec.rs`) запускают
  `cli spec … --json`, то есть тот же парсер, что читают хуки. Rust владеет
  только тем, чего CLI изнутри приложения знать не может, — каталогом проекта:
  доска хранит проект базовым именем, а не путём, поэтому полный `cwd`
  вычитывается из транскриптов Claude Code. Ответы вкладка не редактирует:
  ответ, набранный в форме, снова стал бы отпиской, а не суждением о разделе,
  который гард положил перед сессией.
- Список проектов из транскриптов — это КАЖДЫЙ каталог, в котором хоть раз
  шла сессия: `src-tauri`, скретчпады, чужие `node_modules` (на этой машине их
  52 против одного проекта со спеками). Поэтому `spec_projects` отдаёт флаг
  `has_specs` (есть ли хоть один `<домен>/spec.md` внутри `specRoot`) и
  сортирует такие проекты вперёд, а вкладка на них же и встаёт по умолчанию.
  Пустой ответ обязан называть каталог, в котором искали: «спек нет» иначе
  неотличимо от «вы смотрите не на тот проект» — на этом вкладка уже один раз
  соврала про проект с двумя доменами.
- Текст раздела рендерится `marked` (единственная внешняя зависимость фронта
  под markdown): спека — настоящий markdown с таблицами и вложенными списками,
  а мини-рендерер `insightHelp/render.ts` знает четыре конструкции и таблицу
  сплющил бы молча. Заголовок и строки метаданных из текста вырезаются и
  показываются чипами — значения при этом берутся из разобранного реестром
  `entry`, а не из этой вырезки. Санитайзера нет: это содержимое репозитория
  проекта, тот же уровень доверия, с каким его печатает CLI.
- У каждого блока вкладки — триггер `?` с пояснением (общий `renderInsightHelp`
  и строки i18n, как у плиток аналитики), развёрнутым на месте, а не поповером:
  панель и так скроллится.
- **Список слева переключается между двумя направлениями**: «по разделам»
  (раздел, а рядом номера задач, которые его правят) и «по change'ам» (change, а
  под ним разделы, дельтой которых он является). Второе — не украшение: вопрос
  «куда идёт это изменение» задаётся, когда читатель стоит на change'е, и
  сколько ни размечай разделы, из списка разделов он не отвечается.
- **Пункт раздела несёт на полях задачу, которая его написала.** Раздел
  разбирается на блоки (`sectionBlocks`) — пункт верхнего уровня со своим
  отступным продолжением, — и ответ `updated` записывает хеши тех блоков,
  которых не было в слепке при взятии задачи. Вкладка рендерит раздел по
  блокам и ставит номер задачи на поле. Блок опознаётся по содержимому, не по
  позиции: соседние пункты вставляют и убирают постоянно, и номер строки к
  завтрашнему дню показывал бы на чужой текст, а хеш при правке пункта меняется
  сам — метка переходит к тому, кто правил последним. Пока ни один блок не
  размечен, раздел рендерится одним куском: так он читается лучше. Меток на
  одном пункте может быть несколько, и это не край: два change'а, снявшие
  слепок до того, как ответил любой из них, оба запишут добавленный пункт, а
  удалённый и набранный заново дословно возвращается к тому же хешу.
- **Метка несёт и номер, и цвет.** Номер — имя: цветом задачу не зовут ни
  доска, ни коммиты, ни проза. Цвет — связка: он делает метку на поле, строку
  в списке change'ей и чип в легенде одним объектом, не заставляя глаз
  сличать трёхзначные числа. Тон берётся из номера задачи золотым углом,
  поэтому соседние номера — а именно так нумеруются шаги одного change'а —
  расходятся по кругу, а не сливаются в оттенок. Клик по метке включает
  **фокус**: пункты, которых этот change не писал, гаснут. Фокус доступен
  только тому, у кого записаны блоки, — гасить раздел ради change'а без
  разметки значило бы утверждать, что он не тронул ничего.
- **Change несёт дельту раздела и показывает её как diff.** Метки говорят,
  какие пункты он написал, но не говорят, что эти пункты **заменили**, — а
  правка спеки чаще всего перепись, и старая формулировка после сохранения
  файла не живёт больше нигде. Поэтому слепок при взятии задачи хранит и текст
  (`spec_seen.text`), ответ `updated` дописывает текст на момент правки
  (`spec_answers[].after`), а вкладка сводит их построчным LCS-диффом
  (`src/specDiff.ts`) с хунками и контекстом. Две стороны собираются
  одинаково — блоки через `\n`, — иначе половина различий была бы пробелами.
  Дифф у закрытого change'а **заморожен**: читать его с живого файла значило
  бы каждую неделю отвечать на другой вопрос. У открытого замороженной стороны
  ещё нет, и он считается против файла, каким тот сейчас, — это вид «что вот
  прямо сейчас меняется», и вкладка помечает его как живой, а не выдаёт за
  запись.
- **Спека упомянута в самой задаче**: чип `📘 <домен>#<слаг>` на карточке
  (только собственный адрес — унаследованный повторял бы чип change-root'а на
  каждом шаге под ним) и блок в карточке задачи с адресами и записанными
  ответами гарда. Клик уводит на вкладку Specs, на этот раздел, а не в поповер:
  раздел читается в одном месте, где рядом видны и остальные change'и на нём.
  Блок только на чтение — адрес пишет `todos set spec`, который валидирует его
  реестром, ответ пишет `spec answer`; поле ввода здесь принимало бы адрес,
  который никуда не резолвится, то есть ровно то, чем ссылка быть не должна.
- Уведомления — при переходе задачи в review и done, см.
  usage-tracker#notifications.

## spec-registry — Реестр спек и поле spec задачи

part: устройство
updated: 2026-08-03 · change: t#358

### registry — Реестр, адрес, поле задачи

- Реестр (`scripts/cli/spec.mjs`) читает домен спек
  `docs/specs/<домен>/spec.md`: шапка даёт `id`, `version`, `updated` и
  `location` файла, а разделы объявляются в теле — заголовок
  `## <слаг> — <Название>` и строки метаданных под ним (`part`, `refs`,
  при необходимости `location`, `updated`, `change`). Карты разделов в шапке
  нет: раздел объявлен ровно один раз, поэтому рассогласовывать нечего
  Корень реестра — настройка `specRoot` (`settings.mjs`), по
  умолчанию `docs/specs`.
- Адрес раздела — `<домен>#<слаг>` (например `tasks#done-gate`).
  `resolveAddress` проверяет существование домена и слага и НИКОГДА —
  доступность текста удалённого раздела (это отдельный вопрос, см.
  `showSection`/`location`).
- Поле `spec` задачи (`todos set spec <task> <домен>#<слаг>[,…]`,
  `todos.mjs::setSpec`) — структурная привязка задачи/change'а к одному или
  нескольким разделам спеки, замена старой текстовой пометки
  `spec: tasks §N` внутри description. Каждый адрес валидируется реестром ДО
  записи (`resolveAddress`) — невалидный адрес отклоняет всю запись, а не
  принимается молча.
- **Якорь — адресуемая единица внутри раздела** (`### <слаг> — <Название>`,
  адрес `<домен>#<слаг>/<якорь>`, форма — README §4/§5). Необязателен: раздел
  сплошной прозой остаётся сплошной прозой, обязательная единица заставила бы
  форму диктовать содержание. Своих метаданных у якоря нет — `part`, `refs` и
  провенанс принадлежат разделу; штамп `updated`/`change` тоже ставится на
  раздел, так что провенанс пока грубее ссылки. Зато всё остальное считается
  по якорю: `spec show` отдаёт единицу, а не раздел вокруг неё, слепок
  (`sectionFingerprint`), блоки и дельта — тоже. Проза до первого якоря
  принадлежит разделу. Дубль якоря — ошибка того же рода, что дубль слага.
  Потолок ~120 строк остаётся бюджетом РАЗДЕЛА: раздел — то, что кладут перед
  сессией, и своя квота у каждого якоря отодвинула бы ту же стену, удвоив
  стоимость чтения.
- Матч ранжирует **якоря, а не разделы**, когда раздел на них разбит. Счёт —
  доля покрытой массы запроса, поэтому длинный раздел из разных предметов
  размывает любой запрос; единица в несколько строк — то, над чем эта доля
  вообще осмысленна. Раздел с якорями представлен только ими: иначе контейнер
  и его содержимое конкурировали бы за одно первое место.

### commands — Команды

- Команды: `cli spec domains [--json]` — список доменов и их разделов
  (внешние домены помечены отдельно); `cli spec show <домен>#<слаг> [--json]`
  — текст раздела, либо ответ «домен объявлен, текст недоступен» с указанием,
  чего не хватает (незаклонированный внешний репозиторий);
  `cli spec refs <домен>#<слаг>` — обратные ссылки (кто ссылается на этот
  раздел), вычисляются сканированием всех `refs`, а не хранятся отдельным
  полем; `cli spec lint [--json]` — реестр целиком: раздел без `part`,
  невалидные и висячие `refs`, дубль слага, ссылка на задачу трекера в тексте
  раздела, несуществующий файл среди упомянутых, висячая ссылка задачи на
  раздел, два открытых change'а на один раздел (предупреждение), раздел за
  потолком ~120 строк прозы.
### match — Поиск раздела под задачу

- **Поиск раздела под задачу** — `cli spec match "<текст>" | --task <N>`
  (`scripts/cli/spec-match.mjs`), лексика без эмбеддингов и внешних сервисов:
  токены по буквам и цифрам, срез русских окончаний с полом основы в три
  символа, вес слова — idf по разделам (слово, которое есть везде, весит ноль),
  мешок заголовка втрое тяжелее мешка прозы, счёт — доля значимой массы
  запроса, покрытая разделом. Нормировки по длине раздела нет намеренно: она
  отдаёт первое место самым коротким заглушкам. Слово, которого реестр не
  знает, идёт только в знаменатель — это и есть арифметика ответа «раздела
  под это нет». Ответов три, а не два: кандидаты, честный ноль (с названным
  ближайшим промахом и доменами-кандидатами) и «нельзя судить» — по запросу
  короче двух значимых слов предлагать завести раздел нельзя. Адрес,
  написанный в тексте прямо, резолвится реестром и идёт мимо порога.
  `--task <N>` берёт subject и собственное описание задачи (описание
  change-root'а не берётся: измерено, что оно уводит верный раздел под порог)
  и помечает уже слинкованный раздел как сверку, а не находку. Доску команда
  только читает.
- **Порог 0.3 подобран на глаз, и на него нельзя опираться как на границу.**
  Калибровка — 12 точек: девять задач с уже проставленным `spec` дали
  0.30…0.75 против своего раздела, три посторонних текста — максимум 0.29.
  Классы разошлись на одну сотую, то есть не разошлись. Поэтому промах ниже
  порога всё равно печатается строкой «ближайший»: порог решает, что стоит
  первым, а не что читателю позволено видеть. Известные промахи: составные
  слова не разбираются («автообновление» не сводится к «обновлен»), длинный
  текст размазывается по десятку разделов и уводит верный под порог, большой
  раздел вроде `tasks#ui` лезет вторым почти везде.
- **Скилл `spec-check`** (`.claude/skills/spec-check/SKILL.md`) — обёртка над
  этой командой для этапа плана: кандидаты есть → прочитать `spec show` и
  предложить `todos set spec`; кандидатов нет → спросить, заводим ли раздел, и
  назвать домен с `part`; задача уже слинкована → смотреть на ОСТАЛЬНЫХ
  кандидатов и на то, всплыл ли слинкованный раздел вообще. Советник, а не
  ворота: на доску не пишет, план не блокирует, `docs/specs` не правит. В
  `plan-hook` он намеренно не вшит — хук сделал бы из советника ворота на
  матче, precision которого не измерена.
### lint — Что проверяет lint

- **Упомянутый в разделе файл обязан существовать.** §2 запрещает описывать
  устройство кода потому, что имена протухают, — правило превращает каждое
  такое упоминание в проверяемое утверждение вместо запрета, который всё равно
  нарушают. Претензией считается вставка кода, чья голова похожа на файл: путь
  с разделителем (сверяется и по суффиксу, чтобы читаемое `insightHelp/render.ts`
  было законно) либо голое имя с ИСХОДНЫМ расширением. Голые данные и конфиги
  (`todos.json`, `settings.json`) под правило не подпадают — они чаще живут вне
  репозитория; домашние и абсолютные пути, шаблоны с угловыми скобками и
  ссылки пропускаются тоже. Символ после `::` не проверяется: это не файл.
- **Прогон линта стоит там, где случается сам**: шаг CI на изменение
  `docs/specs/**` (фильтр путей заодно дополнен `scripts/**` — без него PR,
  трогающий только CLI и хуки, не гонял вообще ничего) и внутри гарда закрытия,
  где к жалобе про неотвеченный раздел добавляются ошибки реестра **по этим же
  адресам**. Область узкая намеренно: сессия, которой показали чужие проблемы,
  учится пролистывать всё сообщение целиком.
- Ссылка `t#N` в прозе раздела — ошибка реестра (`taskLinksIn`): номер задачи
  протухает вместе с задачей, а спека её переживает. Единственное разрешённое
  место — строка метаданных `change`, и пишет её машина. Отказ стоит и в
  `spec lint`, и в `spec answer updated`: последний не штампует раздел, пока
  ссылка в нём есть, — момент записи дельты и есть самый дешёвый момент
  починки. `unchanged` не гейтится: раздел этой работой не двигали. Голый `#N`
  правилом не задет — по конвенции проекта это PR или issue.
- Раздел может жить вне этого репозитория (строка
  `location: repo=<ключ> path=<путь>` при заголовке раздела, либо
  `location` объектом в шапке — тогда внешним объявлен весь домен, а файл
  здесь остаётся заглушкой без прозы) — в обоих случаях `spec show`/lint
  отвечают
  «объявлено, текст недоступен» вместо тихой пустоты, если репозиторий (ключ
  из `specRepos` в `settings.json`) не настроен или не читается на этой
  машине.
### guard — Гард закрытия

- Гард закрытия (`stop-hook.mjs::auditSpecAnswers`) требует ответа по
  каждому адресованному разделу, когда сессия переводит слинкованную задачу в
  `review` или `done`. Область та же, что у гарда батона: «эта сессия сама
  двигала задачу» по транскрипту, а не по `updated_at`. Адреса берутся тем же
  `specAddressesFor`, что и впрыск, — спрашивают ровно про то, что показали.
  Оба гарда судятся одним проходом и печатаются одним сообщением: хук
  срабатывает один раз за цикл остановки (`stop_hook_active`), поэтому вторая
  жалоба после первой уже не дошла бы никогда.
- Ответ — команда, а не фраза: `cli spec answer <задача> unchanged|updated
  --text "…" [--address <адрес>]`, запись ложится в поле `spec_answers` задачи
  (`{address, verdict, note, at}`; чем меряется свежесть — ниже). Прозы гард не
  ищет намеренно: соседний гард батона в
  живой сессии отклонил нормальный батон только потому, что следующий шаг был
  написан словами «ПЕРВЫЙ ХОД» мимо словаря `NEXT_RE`, — сопоставление
  формулировок учит переформулировать, а не думать.
- Ответ `updated` дополнительно штампует `updated: <дата> · change: t#N` в
  метаданных раздела (`spec.mjs::stampSection`) — это ЕДИНСТВЕННАЯ запись
  реестра в спеку, во всём остальном он read-only. Штампуется change, а не шаг,
  когда задача висит под change-root'ом. Запись идёт через тот же разбор
  метаданных, что и чтение, а не регулярным выражением поверх файла: строки
  соседних разделов возвращаются на место дословно.
- Один ответ на несколько разделов отклоняется, как и дословный повтор ответа,
  уже данного другому разделу: одинаковая отписка на разные разделы — тот же
  протух на новом слое (README §9). Порог содержательности — 40 символов.
  Выключатель — `specDeltaGuard` в `settings.json` (`on` по умолчанию; на доске
  без ссылок на спеку гард инертен и не стоит ничего).
- **Ответ считается свежим относительно рабочего цикла**, а не начала сессии и
  не текущего статуса: пол берётся из метки слепка `spec_seen[адрес].at`,
  которая ставится ровно на впрыске раздела при переходе в `in_progress`, —
  это буквально «ответ дан про тот текст, который сессия видела». Нет слепка —
  последний вход в `in_progress`; нет и его — начало сессии. Пол считается по
  каждому адресу отдельно: два раздела могли быть показаны в разные моменты, и
  свежесть одного ничего не говорит о другом. Смысл пола — не пустить пачку
  отписок в конце сессии: шаблонный ответ, приходящий не через формулировку, а
  через момент. Первая редакция мерила от перехода в текущий статус и тем
  перевзводила гард на каждом движении задачи: ответить, перевести в review,
  ответить снова, перевести в done, ответить в третий раз — всё про текст,
  который не двигался. Три одинаковых ответа за сессию, то есть ровно тот
  протух из README §9, произведённый самим гардом. Возврат задачи в работу
  снимает старый ответ сам: новый вход в `in_progress` пишет новый слепок.
- **Адрес резолвится на обеих ветках ответа.** Ссылка валидируется при записи,
  но слаг могут переименовать позже, и ответ про исчезнувший раздел снимал бы
  гард, не сказав ничего. Пока `resolveAddress` звала только ветка `updated`,
  дешёвый `unchanged` был единственным неохраняемым путём в механике — а он же
  путь наименьшего сопротивления.
- **Снять ссылку с закрываемой задачи нельзя** (`setSpec` отказывает на
  `review`/`done`): это разоружало гард бесследно — доска после такого
  неотличима от доски, где ссылки не было вовсе. Все прочие обходы в конвейере
  произносят своё имя вслух (`--force`), этот обязан тоже.
- Известные обходы гарда, не закрытые кодом: повторная остановка сессии (хук
  срабатывает раз за цикл), закрытие перетаскиванием в интерфейсе приложения,
  закрытие headless-раннером из хост-процесса, закрытие другой сессией. См.
  README §9 — там они перечислены как границы обещания.
